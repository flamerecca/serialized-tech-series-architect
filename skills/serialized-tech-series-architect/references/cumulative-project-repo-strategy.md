# 累積式程式碼庫與漸進專案演進策略

在 30 至 50 篇的長篇教學系列中，最忌諱每一天都給出一個零散、互相割裂的獨立小範例（Hello World 玩具程式碼）。
本指南說明如何透過「單一累積式專案（Cumulative Capstone Project）」結合 Git 標籤演進，帶領讀者逐步將一個小型骨架專案演進為可上線的生產級系統。

---

## 累積式專案 vs 碎片化範例對比

| 評估維度 | 碎片化範例（反模式） | 累積式專案（推薦最佳實踐） |
| :--- | :--- | :--- |
| **讀者沉浸感** | 讀完依然不知道如何把各個知識點拼裝成完整系統。 | 讀者伴隨專案一同成長，擁有真實的「親手造出輪子」成就感。 |
| **程式碼復用性** | 每一天都要重新寫一遍資料庫連線或入口檔案。 | 前一天的產出直接作為後一天的基礎，每一行程式碼都有價值。 |
| **期末成果展示** | 無法作為履歷或 GitHub 作品集。 | 最終產出一個完整可執行的開源 Repo，具備完整 README 與 CI/CD。 |

## Git 分支與標籤管理策略 (Branch-per-Day & Tag-per-Day)

為了讓落後進度的讀者能夠隨時同步，或讓進階讀者快速跳轉，專案 Repo 必須建立清晰的 Git 標籤體系：

```text
main (最終完整完成版)
├── tag: day-01-project-scaffolding
├── tag: day-02-database-session-lifecycle
├── tag: day-03-crud-models-and-migrations
...
├── tag: day-15-jwt-authentication-middleware
...
└── tag: day-30-docker-compose-production-release
```

### 提供讀者「起點」與「終點」雙重保險

在每篇文章的結尾與附錄中，提供兩種檢驗方式：
1. **起點指令（若讀者卡關或想直接開始今天單元）**：
   ```bash
   git checkout tags/day-14-complete -b my-day-15-practice
   ```
2. **終點對照（若讀者寫完程式碼想核對差異）**：
   ```bash
   git diff tags/day-14-complete..tags/day-15-complete
   ```

## 漸進式重構的核心原則 (Non-Breaking Incremental Refactoring)

在專欄進行到第 15~20 天時，常常需要對第 3~5 天寫下的基礎程式碼進行「效能重構」或「架構抽象」（例如將同步資料庫換成非同步 ORM，或引入依賴注入）。此時應遵循以下原則：

1. **先說明痛點，再進行重構**：
   - 絕不在沒有解釋理由的情況下突然更換目錄結構或函式簽名。
   - 先展示舊程式碼在高併發或擴展時遭遇的瓶頸，再帶出重構方案。
2. **展示清晰的 Before / After 差異**：
   - 標記被修改的檔案路徑與變更行數，避免讀者在龐大的專案中迷失。
3. **保持單元測試綠燈**：
   - 每次重構後，第一件事是執行前幾天寫好的測試，證明重構「只改善結構，未破壞既有業務行為」。
